# Dependencies for the `f1-backend` Cloud Run service.
#
# The service layer is pinned with `~=` (compatible-release): patch updates
# flow, minor ones do not. These were bare names until now, which meant two
# builds of the same commit could install different code.
#
# THE SCIENTIFIC STACK IS DELIBERATELY LEFT UNPINNED. That is not an oversight,
# and it should not be "tidied up" without reading this.
#
# Pinning `pandas~=2.0.1` here broke production. pandas 2.0.1 is compiled
# against the numpy 1.x C ABI; with numpy unpinned, pip installed numpy 2.x
# beside it. Nothing complained -- pip saw no conflict, the image built, the
# image pushed -- and the container then died on startup with:
#
#     ValueError: numpy.dtype size changed, may indicate binary
#     incompatibility. Expected 96 from C header, got 88 from PyObject
#
# An ABI mismatch is invisible to a dependency resolver, so it cannot surface
# until the container actually runs. Pinning numpy alongside pandas fixes that
# one pair and immediately moves the same problem one layer down: fastf1 also
# pulls scipy and matplotlib, whose current wheels are built against numpy 2.x
# and would then become the mismatched ones.
#
# Doing this properly needs a lockfile resolved on linux/amd64 and a container
# to test the import in -- not hand-picked specifiers checked on a Windows
# machine. Meanwhile fastf1's own dependency ranges have resolved a working set
# on every deploy this service has ever had, so they are left to keep doing it.
#
# If you pin them later: pin numpy, pandas, scipy and matplotlib TOGETHER, and
# verify by building the image and importing `app.main` inside it, because
# `pip install` succeeding proves nothing about this class of failure.

# --- Service ---------------------------------------------------------------
